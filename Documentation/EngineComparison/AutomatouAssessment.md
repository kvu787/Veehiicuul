Assessed 2026-09-24. Scope: read-only inspection of source and project documentation in `C:\Users\k\Repository\Automatou`, at commit `e418eb9e2a749ac95b8f6a3eddf58013bb9e7993`. The working tree was clean when inspected. No projects, launchers, or tests were executed; consequently this note contains no measured performance results. Repository conversation archives were not read. All analysis output is confined to `MyAnalysis` as requested.

## Decision relevance

**Automatou currently provides stronger evidence for retaining an engine-independent C# simulation than for choosing a particular renderer.** Its mechanics, automaton programs, and test harness are already separated from Godot presentation. Its likely scaling problems are ordinary CPU algorithms and allocation patterns in that portable simulation, plus per-turn diagnostic logging and UI rebuilding. Moving identical algorithms into Unity, C++, Vulkan, or Direct3D 12 would not remove their complexity.

The current game is a 2D, turn-based, hex-grid world-builder-and-runner. It already uses Godot and .NET, so remaining with Godot has the lowest migration cost for this repository. This does **not** establish that the eventual simulator must remain small, 2D, or visually simple; the user's intended future scale and visuals leave all three platform choices open. Nor does it decide the combined racing-and-simulation platform question by itself.

## Existing separation is valuable

`AutomatonPrograms` references only `AutomatonContract`. Programs receive paid observations, maintain private memory, and submit actions; they do not reference Godot or the authoritative world implementation. See [program project references](C:/Users/k/Repository/Automatou/Automatou2/Source/AutomatonPrograms/AutomatonPrograms.csproj:1), [contract](C:/Users/k/Repository/Automatou/Automatou2/Source/AutomatonContract/SystemCalls.cs:5), and [architectural test](C:/Users/k/Repository/Automatou/Automatou2/Tests/Program.cs:238).

The world freezes physical values at the start of each turn, collects complete action lists from every automaton, then resolves action slots. Conflicting movement destinations all fail, swaps remain blocked, and attack ordering rotates deterministically. That is application-owned simulation semantics, not Godot physics. See [snapshot construction](C:/Users/k/Repository/Automatou/Automatou2/Source/Simulation/TurnResolution.cs:13) and [turn resolution](C:/Users/k/Repository/Automatou/Automatou2/Source/Simulation/TurnResolution.cs:33).

The standalone test executable compiles simulation sources and references the contract/program assembly without Godot. This is direct evidence that the current rules can be evaluated outside the engine. A clean next step would be to give all simulation sources their own ordinary library project rather than source-linking them into tests and the Godot application. See [test project](C:/Users/k/Repository/Automatou/Automatou2/Tests/SimulationTests.csproj:1).

This structure supports solo-plus-AI development: a bounded public contract, a plain command-line test loop, deterministic scenarios, diagnostic explanations, and source-defined unit registration. Preserve these properties under every option. Engine selection alone will not make AI-authored changes correct; repeatable tests and observability are already the strongest assets here.

Two qualifications matter:

1. A contract assembly and exception handling are not a security or CPU-time sandbox for untrusted programs. `RunTurn` is an ordinary synchronous method call. If arbitrary player-supplied code becomes a product requirement, execution isolation, resource budgets, and platform policy become separate work. Current developer-authored C# programs do not require such a product feature.
2. Deterministic replay in the present runtime is tested in source, but cross-platform bit-for-bit determinism is not established. Visibility uses floating-point interpolation/rounding, direction selection uses floating-point math, and behavior scores use `double`. Cross-architecture replay needs explicit validation if it matters. See [visibility](C:/Users/k/Repository/Automatou/Automatou2/Source/Simulation/PerceptionAndNavigation.cs:28), [hex direction](C:/Users/k/Repository/Automatou/Automatou2/Source/AutomatonContract/Hex.cs:47), and [scoring](C:/Users/k/Repository/Automatou/Automatou2/Source/AutomatonPrograms/StandardAutomaton.cs:19).

The frozen planning phase suggests a future parallelization boundary: plan independent automata against immutable data, then reduce outputs in a stable order before resolution. ## Platform and migration implications

### Godot

Keeping Godot retains the current interface, board rendering, scene integration, and testing workflow. The simulation does not need to become node-oriented, and native C++ need not mean abandoning the engine: expensive, measured kernels could eventually move behind a small native boundary while Godot supplies presentation and platform services. The current source offers no evidence that a Godot engine limitation forces that step.

The checked-in project is not currently configured as an Android product. It targets x64; selects Windows D3D12 with Vulkan/OpenGL fallback disabled; assumes desktop mouse/keyboard interaction and a 1100 × 700 minimum window; and defaults logs under `res://MyLogOutput`. These are application assumptions to replace or specialize for mobile. They are not evidence that the engine cannot target mobile. See [project target](C:/Users/k/Repository/Automatou/Automatou2/Automatou.csproj:1), [rendering configuration](C:/Users/k/Repository/Automatou/Automatou2/project.godot:24), and [startup paths/window](C:/Users/k/Repository/Automatou/Automatou2/Source/Interface/MainInterface.cs:53).

The launcher builds the application in **Debug** and starts the Godot executable against the project. Its optional standalone simulation verification builds in Release. Benchmarking this launcher against a release Unity or native build would be invalid. A representative release-export workflow must be part of the platform trial. See [launcher](C:/Users/k/Repository/Automatou/Automatou2/Run.ps1:30). No `Automatou2/export_presets.cfg` was present during this inspection.

### Unity

The domain design, unit definitions, programs, scenarios, and correctness tests are conceptually reusable. The Godot interface and drawing implementation need a Unity replacement, and **sharing the language does not mean this repository compiles unchanged in Unity**.

All three current projects target `net10.0`; the shared build properties select C# 14. The source demonstrably uses newer language features: file-scoped namespaces and record structs, required members, collection expressions, and primary constructors on ordinary classes. It also uses `PriorityQueue` and `MinBy`. See [build properties](C:/Users/k/Repository/Automatou/Automatou2/Directory.Build.props:3), [contract target](C:/Users/k/Repository/Automatou/Automatou2/Source/AutomatonContract/AutomatonContract.csproj:3), [required member](C:/Users/k/Repository/Automatou/Automatou2/Source/Simulation/Definitions.cs:18), and [pathfinder](C:/Users/k/Repository/Automatou/Automatou2/Source/AutomatonPrograms/ActionPlanning.cs:5). The targeted scan found no specifically C#-14-only construct; do not turn the project setting into an unsupported claim about which language features it requires.

The currently retrieved Unity 6000.7 default compiler documentation lists C# 9 with record/init caveats. Microsoft identifies collection expressions and ordinary-class primary constructors as C# 12 features, and `PriorityQueue`/`MinBy` as .NET 6 additions. A conventional Unity import therefore requires language/API adaptation and retargeting. [Unity compiler documentation](https://docs.unity.com/en-us/engine/6000.7/manual/scripting/environment-and-tools/overview-of-dot-net-in-unity/csharp-compiler), [Microsoft C# 12](https://learn.microsoft.com/en-us/dotnet/csharp/whats-new/csharp-12), [Microsoft .NET 6](https://devblogs.microsoft.com/dotnet/announcing-net-6/).

This is changing: Unity's 6000.7 **experimental** MSBuild documentation describes an opt-in `net10.0` path using `enablelastdotnet.config`, alongside its usual `netstandard2.1` path. It would therefore be inaccurate to say Unity can never host .NET 10. Pin the exact Unity release, scripting backend, supported target platforms, and production status before choosing between retargeting and an emerging runtime. The existence of a newer desktop/editor path does not establish release-ready Android parity. [Unity experimental MSBuild](https://docs.unity.com/en-us/engine/6000.7/manual/scripting/compilation-and-code-reload/script-compilation/msbuild).

A useful Unity feasibility spike imports only the contract, programs, simulation library, and tests first. It should produce a concrete compile-error/API inventory and run the same deterministic scenario before recreating the entire UI. Adopting Entities/Jobs/Burst is an additional architecture choice; the current object graph, inheritance, records, managed lists, and callbacks are not automatically transformed into a data-oriented simulation by importing them.

### C++ with Vulkan / Direct3D 12

There are two different proposals hidden in this option:

1. Reimplement the entire simulator and its tools in native C++, including rendering and platform integration.
2. Retain a managed rules core and build a native shell, or retain Godot/Unity and accelerate selected simulation modules in native C++.

Only the first is a complete engine replacement, and it discards the most code. The second can pursue control and performance incrementally but creates a managed/native ABI, build, and deployment obligation. Prefer coarse buffers and operations at that boundary over per-unit/per-cell calls.

For today's Automatou mechanics, Vulkan/D3D12 do not supply perception, navigation, turn resolution, world editing, inspectors, checkpoint semantics, save formats, or UI layout. Those are the valuable parts of this codebase. A custom renderer may become justified by a future demonstrable visual requirement, but this repository supplies no such requirement today. Choosing C++ for ownership or system-design preferences remains legitimate; it should be chosen with the full tooling and portability cost counted.

## Historical code that is useful without confusing it with the current prototype

`Automatou1` explicitly separates a mandatory .NET kernel from optional shells. Its original shell protocol uses JSON Lines and a separate host executable; it includes a terminal shell. This is useful prior work for command contracts, a headless harness, and shell independence, but do not apply its process boundary to `Automatou2`, which calls the simulation in-process. The older Godot shell's name is `SimplePaint3DShell`, although its README describes a symbolic 2D implementation and a future 3D direction. See [original architecture](C:/Users/k/Repository/Automatou/Automatou1/Documentation/Architecture.md:3) and [original README](C:/Users/k/Repository/Automatou/Automatou1/README.md:11).

`RectangularGridMotion` is a small integer-only motion/turn-reservation experiment. Its quarter-turn rules do not claim to model continuous rigid-body rotation. It can inform grid mechanics and edge-case tests, but it is not evidence of a racing-vehicle physics engine. See [experiment scope](C:/Users/k/Repository/Automatou/RectangularGridMotion/README.md:3) and [reservation limits](C:/Users/k/Repository/Automatou/RectangularGridMotion/README.md:40).

## A benchmark that could change the decision

Do not demand a million-agent world unless that becomes a real design target. Use a small reproducible suite and find the scaling curve. The following are **proposed test points, not supported capacity claims**:

| Test tier              | Suggested workload                                                                                                               | Purpose                                                                                                              |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Current reference      | Existing 816-cell / 28-unit encounter and the focused heat, concealment, spacing, and bond scenarios.                            | Preserve behavior and establish reference hashes, replay behavior, and baseline overhead.                            |
| Moderate population    | 5,000-cell map with 100 and 500 size-one units; mix larger bodies in a separate case.                                            | Expose perception, pathfinding, logging, and memory growth before rendering becomes a distraction.                   |
| Current authoring edge | 20,000-cell map with 1,000 units, then increase if viable; separate dense crowds, chokepoints, and dispersed groups.             | Distinguish density/pathological contention from raw population.                                                     |
| Growth experiment      | A copied benchmark harness may bypass the 20,000-cell application guard for larger sparse maps and higher populations as needed. | Test future design hypotheses without treating the present authoring guard as an engine limit or a product promise.  |
| Presentation stress    | Fit all cells, zoomed-in view, sustained camera movement, effects active, no unit selected versus inspector visible.             | Separate draw/geometry/GC cost from simulation and UI rebuilding.                                                    |
| Shipping/mobile        | Same scenarios in an optimized Windows build and an actual intended Android device, including a sustained run.                   | Validate real packaging, touch workflow, memory, power/thermal behavior, and frame pacing.                           |

Record median/p95/p99 simulation turn time, end-to-end frame time, main-thread stall time, allocated bytes per turn, GC events, peak working set, snapshot/restore time, perception candidate counts, path expansions, conflict candidates, log volume, and replay hashes. Run three modes: simulation alone with rendering/logging excluded; presentation of a fixed world; full application with normal diagnostics and then buffered/disabled diagnostics. Use the same seed, maps, programs, inputs, build optimization, and visual workload across engines.

Start with the current C# core and one inexpensive algorithm pass. A portable simulation library makes this a relatively small investment: it measures the part of the game common to all options. If simulation-only performance is acceptable but the full Godot presentation is not, optimize or replace presentation. If the rules dominate, measure algorithm/data-layout improvements before attributing the cost to the engine. If a carefully optimized C# core still misses a real design target, port one identified hot kernel to C++ or a Unity data-oriented implementation and compare identical results.

For a 60 Hz presentation target the frame interval is about 16.7 ms. A simulation running eight turns per second has a 125 ms turn interval, but a synchronous 100 ms turn still causes a noticeable UI/render stall; average turns per second alone is therefore insufficient. A worker simulation with immutable presentation snapshots may be a better response than accelerating rendering. That architecture must preserve pause/edit/rewind semantics and deterministic publication order.

## What remains uncertain

- No measured CPU/GPU profile, allocation trace, release-export test, Android test, or cross-platform replay test was performed.
- Final agent counts, active-world extent, persistent-world size, simulation frequency, desired visual complexity, and multiplayer requirements are deliberately not assumed.
- The current architecture is particularly favorable to replayable discrete simulation. A future continuous physical world, broad economy, streaming geography, or player-programmable runtime could change data and tooling requirements substantially under any engine.
- Godot's exact Android .NET support and Unity's exact production runtime/target matrix must be evaluated against the releases chosen for the main report; repository version strings alone cannot settle those external facts.

The practical contribution of this repository to the decision is clear: **preserve the simulation boundary and compare shipping workflows and measured bottlenecks.** Continuing Godot is easiest for Automatou today; moving to Unity is feasible but includes a substantial presentation migration and a concrete runtime-compatibility exercise; full native development is a broader rewrite whose strongest justification would have to come from control/ownership preference or demonstrated future requirements, not the current grid mechanics.
