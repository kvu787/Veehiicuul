## Stable documentation cross-check

**Rendering.** Godot 4.7 documents Forward+, Mobile, and Compatibility. The first two use RenderingDevice and can use modern graphics drivers; Compatibility uses OpenGL. Their feature sets and costs differ. For these modest 2D/2.5D games, benchmark Compatibility or Mobile before assuming Forward+ is preferable. Keep optional high-end effects separate from gameplay. [Renderer overview](https://docs.godotengine.org/en/4.7/tutorials/rendering/renderers.html).

**C# deployment.** Official 4.7 documentation supports C# on Windows, Linux, macOS, Android, and iOS, while marking Android and iOS experimental. It does not support official Godot 4 C# web export. These are distinct from the reach of non-C# Godot projects. [C# platform support](https://docs.godotengine.org/en/4.7/tutorials/scripting/c_sharp/index.html).

**Threading.** Godot supports worker computation and server APIs, but the active scene tree is not generally safe to manipulate from arbitrary threads. The documented separate rendering-thread mode also has known caveats. The simplest reliable design is background work on owned simulation data, followed by a bounded main-thread presentation update. [Thread-safe APIs](https://docs.godotengine.org/en/4.7/tutorials/performance/thread_safe_apis.html).

**Bypassing node overhead.** RenderingServer and PhysicsServer can be used without creating one scene node per simulated object. Synchronous information requests to asynchronous servers can introduce stalls. [Using servers](https://docs.godotengine.org/en/4.7/tutorials/performance/using_servers.html).

**Managed collections.** Godot collection wrappers involve marshaling. Use .NET collections for internal C# calculations and convert only when engine APIs require it. [C# collections](https://docs.godotengine.org/en/4.7/tutorials/scripting/c_sharp/c_sharp_collections.html).

**Native escape hatch.** GDExtension loads native shared libraries without recompiling the whole engine. A native simulation library can remain engine-independent with a small adapter. That is a much smaller commitment than owning a complete renderer and content pipeline. [GDExtension](https://docs.godotengine.org/en/4.7/engine_details/engine_api/gdextension/what_is_gdextension.html).

**Coordinate precision.** Double precision has memory/performance costs and is not automatically the right mobile choice; local coordinates or origin shifting remain alternatives. No stated requirement currently justifies a custom double-precision engine build. [Large world coordinates](https://docs.godotengine.org/en/4.7/tutorials/physics/large_world_coordinates.html).

**Support.** Godot's stable branch maintenance is best effort and encourages tested updates. Open source permits retaining a version, but does not guarantee indefinitely maintained export SDKs or a free fix for every issue. [Release policy](https://docs.godotengine.org/en/4.7/about/release_policy.html).

## Conclusion

Godot provides enough architectural escape hatches that choosing it does not trap all future performance work in a high-level scripting or scene-node model. Its source availability has particular value when AI assists with tracing concrete engine behavior. The practical limits are the cost of understanding and maintaining those changes, the C# mobile maturity caveat, and the absence of official C# web deployment. None of the inspected source proves a performance win over Unity or a native renderer for these games.
