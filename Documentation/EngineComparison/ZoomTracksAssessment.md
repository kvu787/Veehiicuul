# ZoomTracks and Unity: evidence for the platform decision

Prepared 2026-09-24 (America/Los_Angeles). This is a read-only source assessment, with official Unity documentation checked during the analysis. No editor, game, build, tests, or benchmark was run. Existing test code is evidence of testability, not a fresh passing result or a measured performance result.

The inspected ZoomTracks checkout was clean at `9fc72ce7acdc22efe05d4415d9d6a9391cd05f66`. Local line references describe this snapshot. Physical source counts exclude editor scripts, tests, packages, generated project files, and Blender code unless stated otherwise.

## What the actual racer needs

The current game is materially simpler than the phrase “racing game” might suggest. Its own [README description](C:/Users/k/Repository/ZoomTracks/README.md:11) specifies a flat 2D simulation, static environment, overhead three-quarter presentation, optional unlit 3D car, and no elevation, dynamic lighting, shadows, or moving world objects. These are current project facts, not proposed constraints on future games.

This means the immediate decision is primarily about iteration, content import, presentation, input, shipping, and reliable timing. It is not currently a contest between PhysX, Jolt, and a custom vehicle dynamics engine. Unity's wheel suspension and tire-friction features could become useful for a substantially different racing design, but the [official WheelCollider workflow](https://docs.unity3d.com/6000.3/Documentation/Manual/WheelColliderTutorial.html) does not describe what ZoomTracks presently implements.

All three candidate platforms can express the current racer. Keeping Unity has the smallest immediate change cost. Moving this racer to Godot C# is a bounded adaptation with substantial reusable logic and assets. Moving to C++ plus a renderer is possible, but it replaces considerably more infrastructure and forfeits direct reuse of the C# implementation unless the project also takes on a managed/native interop arrangement.

## Architecture, coupling, and reusable work

The central [Main lifecycle](C:/Users/k/Repository/ZoomTracks/ZoomTracks/Assets/Scripts/Main.cs:68) loads UI and track scenes additively, constructs ordinary C# manager objects, and enters an async loop that yields once per rendered frame with `Awaitable.NextFrameAsync`. This is not a large collection of independent per-object `Update` components. The design is relatively straightforward for AI to inspect because sequencing is explicit.

The main boundaries are:

| Area                   | Current implementation                                                                                                     | Portability assessment                                                                                         |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Track authoring        | Blender Python TrackBuilder; outlines, generated meshes, barrier segmentation, materials, regression fixtures              | High reuse across all engine choices; output destinations and import conventions need adaptation               |
| Track data             | Exported JSON outlines and per-track settings                                                                              | High reuse if coordinate and schema contracts remain explicit                                                  |
| Collision algorithm    | Pure C# geometry, spatial grid, oversized-edge BVH, robust segment predicates                                              | Direct C# reuse in a compatible host; C++ requires a validated translation                                     |
| Motion                 | Custom acceleration, braking, velocity limiting, and position integration                                                  | Algorithm reusable; current input/vector/time/transform access needs an adapter                                |
| Rendering/camera       | Unity Transform, Camera, URP camera data, URP quality settings                                                             | Rewrite or translate for Godot/custom platform                                                                 |
| UI/input/scene loading | Unity Input System, UGUI/TMP, scene management, async Awaitable lifecycle                                                  | Rewrite adapters and presentation wiring; preserve the underlying interaction design                           |
| Desktop diagnostics    | Command-line parameters, timing logger, desktop graphics settings, external display/GPU configuration                      | Retain measurement intent; use platform-specific implementations and avoid copying desktop defaults to mobile  |

[CarState](C:/Users/k/Repository/ZoomTracks/ZoomTracks/Assets/Scripts/GameDataAndLogic/Car/CarState.cs:73) reads a gamepad trigger and stick, transforms acceleration into car/world coordinates, integrates velocity and position, and aligns heading to velocity. It finally [writes a Transform directly](C:/Users/k/Repository/ZoomTracks/ZoomTracks/Assets/Scripts/GameDataAndLogic/Car/CarState.cs:145). The active movement path does not use a Rigidbody or WheelCollider.

[CollisionManager2](C:/Users/k/Repository/ZoomTracks/ZoomTracks/Assets/Scripts/GameDataAndLogic/CollisionManager2.cs:25) is a reasonably narrow adapter: load outline JSON, derive mesh footprint, read current car transform, and call the detector. [TrackCollisionDetector](C:/Users/k/Repository/ZoomTracks/ZoomTracks/Assets/Scripts/GameDataAndLogic/CollisionDetection/TrackCollisionDetector.cs:63) indexes ordinary edges by bounds center and uses a separate strategy for oversized edges. It imports `System` namespaces, not `UnityEngine`. Its exact-orientation fallback uses [BigInteger arithmetic](C:/Users/k/Repository/ZoomTracks/ZoomTracks/Assets/Scripts/GameDataAndLogic/CollisionDetection/TrackCollisionDetector.cs:1190). Preserve those contact semantics during a port rather than replacing them with a generic engine collision API and assuming equivalent results.

The detector answers whether the vehicle perimeter intersects track outlines at a supplied pose; it is not a complete swept vehicle dynamics solver. The [main loop intentionally displays overlap and resets on the next iteration](C:/Users/k/Repository/ZoomTracks/ZoomTracks/Assets/Scripts/Main.cs:171). A future design that needs continuous collision, impulse response, multiple dynamic vehicles, or physical suspension changes the gameplay requirements independently of engine selection.

The codebase is not presently locked into third-party vehicle middleware or an asset-store framework. The package manifest lists Unity packages, and the inspected Assets tree contains the project's own scripts/assets plus TextMesh Pro resources. This does not audit ownership or licenses of every mesh/font, and does not prove that all future asset purchases will be portable. It does show that “Unity's ecosystem would be hard to leave” is not strongly supported by the current gameplay dependency graph.

## Existing tests and content pipeline

The [standalone collision harness project](C:/Users/k/Repository/ZoomTracks/CollisionDetection/ZoomTracksProductionTests/ZoomTracksProductionTests.csproj:12) compiles five production collision/data files directly into a .NET 10 executable. It is therefore concrete evidence that this subsystem can operate independently of Unity. Its [documented coverage](C:/Users/k/Repository/ZoomTracks/CollisionDetection/ZoomTracksProductionTests/README.md:27) includes actual Track001 JSON, optimized-versus-linear comparison, contact semantics, random and every-edge neighborhoods, sparse grids, oversized edges, allocation checks, and comparative timings.

The harness [declares 8,192 deterministic random queries and 100,000 allocation-check queries](C:/Users/k/Repository/ZoomTracks/CollisionDetection/ZoomTracksProductionTests/Program.cs:11). These counts describe the test program; this assessment did not execute it, and its .NET 10 timings would not substitute for Unity Mono/IL2CPP or Android measurements.

There is also a [Unity editor integration validator](C:/Users/k/Repository/ZoomTracks/CollisionDetection/ZoomTracksProductionTests/README.md:48) that checks the imported FBX footprint and collider coordinate mapping. That distinction is valuable: a mathematically correct detector can still be wrong in-game if the importer changes scale, handedness, orientation, or child transforms.

TrackBuilder has an extensive [Blender regression and rollback suite](C:/Users/k/Repository/ZoomTracks/Blender/TrackBuilder/Documentation/TEST.md:66), including golden geometry and adaptive curve cases. This authoring investment survives any engine decision. The [track creation instructions](C:/Users/k/Repository/ZoomTracks/Documentation/HowToCreateANewTrack.md:21) export FBX plus JSON and then perform Unity scene/import setup. The current documented map is [Unity X/Z = negative Blender X/Y](C:/Users/k/Repository/ZoomTracks/CollisionDetection/ZoomTracksProductionTests/README.md:23); a Godot or custom importer needs an explicit checked mapping, not an assumed copy of this convention.

Content setup still includes manual scene duplication, import settings, scene-list registration, and edits to the track-name list. This is a concrete solo-plus-AI productivity opportunity in either engine: retain Blender authoring, define a track descriptor, and automate repeatable engine-side setup. A custom renderer could streamline the narrow format, but the format advantage does not require owning a renderer.

## Maturity and timing limitations relevant to lock-in

There is useful gameplay and a unusually deliberate geometry test setup, but the inspected racer is not evidence of a finished shipping pipeline. For example, [lap timing/checkpoint progression and persistence are comments in the main loop](C:/Users/k/Repository/ZoomTracks/ZoomTracks/Assets/Scripts/Main.cs:142), and the [authoring instructions state checkpoint functionality is not implemented](C:/Users/k/Repository/ZoomTracks/Documentation/HowToCreateANewTrack.md:6). This is an advantageous time to establish cleaner engine boundaries, although migrating still carries real validation work.

[TimeManager](C:/Users/k/Repository/ZoomTracks/ZoomTracks/Assets/Scripts/GameDataAndLogic/TimeManager.cs:29) supplies either `Time.deltaTime` or a constant `1 / RefreshRate`. Because the containing loop runs once per presented-frame iteration, the constant mode is not an accumulator-driven fixed simulation loop: missed frames do not automatically execute missed simulation steps. The variable mode is frame-time dependent numerical integration. Neither observation is an engine defect; both describe a game-loop choice that can be retained or improved in any candidate platform.

The repository contains considerable [desktop display and graphics-backend investigation](C:/Users/k/Repository/ZoomTracks/README.md:25), including external driver settings and high-refresh displays. Treat this as evidence that frame pacing and input-to-display latency are a real project priority. Do not turn hardware-specific observations into a universal claim that Unity stutters or DX12/custom C++ is automatically smoother. Driver state, presentation mode, display refresh, compositor, scheduling, queue depth, background work, and instrumentation also affect the result.

The source includes an [Editor queue-depth workaround](C:/Users/k/Repository/ZoomTracks/ZoomTracks/Assets/Scripts/GameDataAndLogic/GraphicsSettingsManager.cs:96) documented by its author as avoiding a DX12 fence wait. That source comment is evidence of a local workaround, not verification here that the referenced issue is still open or that the diagnosis is complete.

The [StutterLogger](C:/Users/k/Repository/ZoomTracks/ZoomTracks/Assets/Scripts/GameDataAndLogic/StutterLogger.cs:17) disables reports in variable-delta mode; the [default command-line path selects variable delta](C:/Users/k/Repository/ZoomTracks/ZoomTracks/Assets/Scripts/Main.cs:234). In the logging mode, the [logger measures intervals between loop visits and flushes on an outlier](C:/Users/k/Repository/ZoomTracks/ZoomTracks/Assets/Scripts/GameDataAndLogic/StutterLogger.cs:35). This is not a presented-frame trace or input-to-photon measurement, and synchronous disk output can itself perturb timing. A platform comparison should use the same scene/input workload and external presentation measurements, with diagnostic logging separated from clean runs.

## Android: a credible Unity path with specific remaining work

Unity 6.3 documents Android 7.1/API 25 or newer, Vulkan/OpenGL ES support, and support for URP but not HDRP. The current URP choice is therefore aligned with Windows plus Android. [Unity 6.3 Android compatibility](https://docs.unity3d.com/6000.3/Documentation/Manual/android-requirements-and-compatibility.html) and [URP graphics API compatibility](https://docs.unity.com/en-us/engine/6000.3/manual/render-pipelines/universal-render-pipeline/requirements) support this assessment. An Android export target does not make the current game mobile-ready.

The current blockers/adaptation needs are specific:

1. **Asset reads.** [JsonUtility.cs](C:/Users/k/Repository/ZoomTracks/ZoomTracks/Assets/Scripts/Utility/JsonUtility.cs:7) replaces URI/path slashes with Windows backslashes and uses `File.Exists` and `File.ReadAllText` on `Application.streamingAssetsPath`. Unity explicitly requires URL-style loading such as UnityWebRequest for packaged StreamingAssets on Android. Use a platform-aware loader or imported runtime assets. [Official StreamingAssets API](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Application-streamingAssetsPath.html).
2. **Input design.** [Driving returns without a Gamepad](C:/Users/k/Repository/ZoomTracks/ZoomTracks/Assets/Scripts/GameDataAndLogic/Car/CarState.cs:73). If ordinary phones without controllers are a target, touch controls, UI navigation, remapping, and pause/resume behavior must be designed and tested. An input abstraction is useful in both Unity and Godot.
3. **Frame pacing policy.** [GraphicsSettingsManager](C:/Users/k/Repository/ZoomTracks/ZoomTracks/Assets/Scripts/GameDataAndLogic/GraphicsSettingsManager.cs:109) uses `targetFrameRate=-1`; its default VSync mode is off. Unity documents this combination as a 30-fps Android default, not the uncapped desktop behavior. Choose explicit mobile rates and test sustainable pacing and thermals on real devices. [Official targetFrameRate behavior](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Application-targetFrameRate.html).
4. **Quality defaults.** A [Mobile_RPAsset](C:/Users/k/Repository/ZoomTracks/ZoomTracks/Assets/Settings/Mobile_RPAsset.asset:26) exists, but [runtime defaults](C:/Users/k/Repository/ZoomTracks/ZoomTracks/Assets/Scripts/GameDataAndLogic/GraphicsSettingsManager.cs:120) apply 8x MSAA and render scale 1. The asset alone is not evidence of a validated mobile configuration. Device-tier presets should control these overrides.
5. **Shipping integration.** Validate the Android player, IL2CPP/ARM64, packaged file access, storage, suspend/resume, display cutouts, orientation/aspect ratios, controller/touch behavior, and sustained power use. The checked project has Android settings, but no tested release readiness is established by this read-only inspection.

The first three are strong reasons to do an Android slice early under whichever platform is selected. They are not grounds to exclude Unity; they demonstrate the difference between engine support and application portability.

## Jobs, Burst, ECS, and larger future simulations

Unity offers a genuine performance-development advantage if the world simulator benefits from parallel numeric workloads and the developer accepts the corresponding data layout. [Burst](https://docs.unity3d.com/6000.3/Documentation/Manual/script-compilation-burst.html) can compile a supported C# subset to native code and can be used without ECS. [Jobs require suitable thread-safe data](https://docs.unity3d.com/6000.3/Documentation/Manual/job-system-thread-safe-types.html), while [Entities 1.4.8 is released for Unity 6.3](https://docs.unity3d.com/6000.3/Documentation/Manual/com.unity.entities.html).

However, this is an available optimization path, not a measured advantage of the present game or an automatic speedup for arbitrary existing C#. ZoomTracks already receives [Burst and Collections transitively](C:/Users/k/Repository/ZoomTracks/ZoomTracks/Packages/packages-lock.json:3), partly through rendering/profiling packages, but its gameplay is not written as Jobs/Burst/Entities code. Its managed collision classes, dictionaries/lists, and BigInteger exact fallback cannot simply acquire a Burst annotation and preserve all behavior unchanged. Ordinary C# tasks/threads remain an option for suitably independent work; ECS should be justified by workload and ergonomics rather than engine marketing.

For a much larger simulator, compare the actual existing core against: (a) ordinary C# on its current modern .NET runtime; (b) an algorithmically equivalent Unity implementation; and, only where needed, (c) a deliberately rewritten Jobs/Burst kernel. Keep simulation time and rendering budgets separate. A rewrite to ECS or C++ may be valuable, but it has a cost and should be evaluated against the same data and semantics.

## Migration implications

**Remain on Unity for the racer:** lowest short-term disruption. Preserve all current assets, camera/input/settings code, and test harnesses; fix the mobile and timing boundaries. This is the rational baseline if the racer is the next release and consolidation can wait.

**Move the racer to Godot C#:** moderate integration work, with strong reuse. Carry over TrackBuilder, source `.blend` assets, outline JSON, collision data and algorithms, tests, and the motion formulas. Replace scene import/setup, Transform and vector bindings, camera behavior, input, UI, URP-specific quality controls, asset loading, and logging paths. Validate materials/colors/antialiasing and coordinate mapping against the existing player. This is substantially less than recreating a complex racing physics stack because the game does not presently have one.

**Move the racer to C++ plus Vulkan/DX12:** higher total burden even though this particular visual workload is small. Reuse data, Blender tools, and test cases; port C# algorithms and preserve robust numeric edge cases. Supply application lifecycle, input, audio when needed, UI/text, asset loading, platform storage, diagnostics, rendering resources, presentation, and packaging. A small renderer may suit the static-scene racer, but the long-term commitment must also cover the simulator and Android. Graphics APIs themselves do not provide these game-platform services.

No calendar estimate is defensible without executing a representative import-and-play slice and establishing acceptance criteria. Source line count alone is not a reliable migration-cost predictor: visual matching, input latency, mobile behavior, robust geometry, and repeatable packaging can dominate.

For the overall decision, the strongest project-specific conclusion is that **ZoomTracks provides a good reason to retain Unity when minimizing immediate racer disruption, but a weak reason to choose Unity permanently for both games**. Its most specialized tested work is already outside Unity or in plain C#. The competing question is whether moving the current simulator into Unity creates more language/runtime/adapter work than moving this comparatively narrow racer into Godot.

A targeted follow-up confirms actual Automatou2 compatibility work beyond its declared language version: [World uses collection expressions](C:/Users/k/Repository/Automatou/Automatou2/Source/Simulation/World.cs:21), [AutomatonKernel uses a primary constructor](C:/Users/k/Repository/Automatou/Automatou2/Source/Simulation/AutomatonKernel.cs:7), [Hex is a record struct](C:/Users/k/Repository/Automatou/Automatou2/Source/AutomatonContract/Hex.cs:4), and [ActionPlanning uses PriorityQueue](C:/Users/k/Repository/Automatou/Automatou2/Source/AutomatonPrograms/ActionPlanning.cs:79). Its surrounding code also uses file-scoped namespaces and `MinBy`. These are concrete changes needed for the documented Unity 6.3 baseline, not proof that the simulator needs a conceptual rewrite. See [the separate Automatou assessment](C:/Users/k/Repository/External/godot/MyAnalysis/AutomatouAssessment.md) for the current simulator's boundaries and test coverage. The adapter scope in both games is small enough that claiming a tenfold migration-cost difference would be unjustified without a prototype.

The strongest affirmative case for Unity is established Android support combined with preservation of the existing racer, supported platform tooling, and an optional Jobs/Burst path for demanding simulation kernels. If avoiding uncertainty in a near-term C# Android release takes precedence over modern .NET ergonomics and engine source ownership, Unity remains a serious alternative. That argument is stronger than generic claims about better vehicle physics or needing ECS, neither of which is established by these projects.

## Proposed acceptance slice before committing to a migration

Use one representative complex track and one car, preserve the collision oracle, and record the existing expected camera framing and colors. A candidate slice should import/export the same content, run the same driving inputs, agree on collision results, switch/reset correctly, and produce a standalone Windows build plus one real Android build with appropriate controls. Measure clean presentation traces at the user's preferred Windows refresh rates and sustained Android frame pacing; separately measure simulation CPU time and allocations. Keep scope small enough to finish while exposing coordinate conversion, rendering quality, file access, input, timing, and export-tool risks.

This is a decision experiment, not permission to maintain three production engines indefinitely. Once a platform is selected, retain portable gameplay data and tests, adopt that platform's normal tooling, and isolate only the boundaries that are genuinely expensive to change.
