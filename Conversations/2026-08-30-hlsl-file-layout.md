# HLSL file layout

Date: 2026-08-30

Repository: `Simple_DirectX12_3D_Game`

## User

> is hlsl shader code always in this format: C:\Users\k\Repository\Simple_DirectX12_3D_Game\src\SceneShader.h ?
>
> can it be in a separate hlsl file or something like that

## Assistant

No. `SceneShader.h` embeds normal HLSL in a C++ raw string so the executable can compile it from memory. The project passes that string to `D3DCompile`; the supplied name `SceneShader.hlsl` is only a diagnostic source name and does not refer to an actual file.

HLSL is commonly stored in a separate `.hlsl` file. It can be compiled at runtime with `D3DCompileFromFile`, although that requires locating and shipping the source file, or compiled during the build into shader bytecode (`.cso`/DXIL), which the application loads without shipping the source or compiler. Build-time compilation is the recommended production layout; runtime file compilation is convenient during development. Vertex and pixel entry points may share one `.hlsl` file, as they do here, or use separate files.

For this project, a clean layout would be `shaders/Scene.hlsl`, compiled twice for `VSMain` and `PSMain`. Because the renderer currently uses the legacy `d3dcompiler` API and Shader Model 5.1 targets, moving the text to a file is a small change; adopting modern Shader Model 6 would instead use DXC.

## User

> For this project, I’d use shaders/Scene.hlsl and compile it twice—once for VSMain and once for PSMain.
>
> why would you "compile it twice" if there is only one file?

## Assistant

Because a shader compilation produces bytecode for one entry point and one pipeline stage, not one output for the entire source file. `Scene.hlsl` contains two separate GPU programs: `VSMain` is compiled with the vertex-shader target `vs_5_1`, and `PSMain` is compiled with the pixel-shader target `ps_5_1`. This produces two distinct bytecode blobs, which DirectX 12 places into the vertex-shader and pixel-shader fields of the pipeline state respectively.

“Compile it twice” therefore means running the compiler twice against the same source text with different entry-point and target arguments. This project already does exactly that at runtime in `Renderer.cpp`. Splitting the functions into `SceneVS.hlsl` and `ScenePS.hlsl` would still require two compiler invocations—one per shader stage.

## User

> i definitely want a separate hlsl file that contains both the vertex and pixel shader. beyond that, i'm unsure. explain what my options are and trade-offs

## Assistant

With one external `shaders/Scene.hlsl` containing both entry points, there are two independent choices: when to compile it and where to store the two resulting bytecode blobs.

Runtime compilation from the `.hlsl` file is the smallest change to this project. Replace the embedded source and `D3DCompile` with `D3DCompileFromFile`, compiling `VSMain` as `vs_5_1` and `PSMain` as `ps_5_1`. It gives convenient source-level diagnostics and permits shader edits without recompiling the C++ executable, but the application must locate and ship the `.hlsl`, startup does compiler work, syntax errors become runtime failures, and the application retains a dependency on the legacy compiler DLL. It is good for a small learning project or a development hot-reload path, but less robust for distribution.

Build-time compilation turns `Scene.hlsl` into separate vertex and pixel bytecode files, conventionally `.cso`. CMake invokes the shader compiler twice and treats shader errors as build errors. The application starts faster, does not expose HLSL source, and does not need to compile shaders on users' machines. The costs are additional CMake commands and the need to deploy and locate the two generated files beside the executable. This is the usual straightforward production arrangement.

Build-time compilation can instead embed the generated bytecode into the executable, either as generated C++ arrays or Windows resources. This retains a separate, editable `.hlsl` source file in the repository while producing a self-contained executable without shader-path or missing-file problems. The trade-off is more build plumbing, somewhat larger executable size, and no ability to replace shaders without rebuilding the program. This is attractive for a tiny demo distributed as one executable.

The compiler is a separate choice. Retaining `D3DCompile`/FXC and Shader Model 5.1 minimizes changes and is sufficient for the current shader. Moving to DXC and Shader Model 6 produces DXIL, provides the modern HLSL toolchain and newer language/hardware features, and is the better long-term direction, but requires configuring and distributing the DXC tooling for compilation and selecting appropriate target versions. Runtime DXC compilation is possible, but adds more application dependencies and complexity than this project currently warrants.

A hybrid development/release setup can compile from source at runtime in debug builds and load precompiled bytecode in release builds. It provides a fast shader-editing loop plus robust releases, but introduces two shader-loading paths that both require testing. It is most useful after hot reload becomes an explicit goal.

The recommended next step for this project is one `shaders/Scene.hlsl`, build-time compilation into `SceneVS.cso` and `ScenePS.cso`, and loading those files at startup. Staying with Shader Model 5.1 first keeps this file-layout change small; DXC can be adopted separately so that source organization and compiler migration do not become one larger change. Embedding the compiled blobs is a reasonable alternative if a single-file executable matters more than simple build logic.

## User

> explain what these are:
> FXC
> Shader Model 5.1
> DXC
> Shader Model 6

## Assistant

FXC and DXC are compiler toolchains; Shader Model 5.1 and Shader Model 6 are compilation targets and GPU capability contracts. The compiler answers “what program translates the HLSL?” while the shader model answers “what kind of shader bytecode and feature level should it generate?”

FXC is Microsoft's legacy HLSL compiler, exposed as `fxc.exe` for build-time use and through the `D3DCompile` functions in `d3dcompiler_47.dll` for in-process compilation. It produces the older DXBC bytecode format and supports the Shader Model 5.x generation. This project currently uses its `D3DCompile` API rather than invoking `fxc.exe` directly.

Shader Model 5.1 is the final target generation used with the legacy compiler. Target strings such as `vs_5_1` and `ps_5_1` combine a stage (`vs` or `ps`) with the shader-model version. It provides everything this project's simple transforms, lighting, buffers, and textures would need and includes DirectX 12-oriented resource-binding improvements, but it does not expose later Shader Model 6 features. Its compiled representation is DXBC.

DXC is Microsoft's modern, LLVM/Clang-based DirectX Shader Compiler, available as `dxc.exe` and `dxcompiler.dll`. It provides improved HLSL language support, diagnostics, optimization, and active support for modern shader targets. For DirectX it normally emits DXIL bytecode. It is the standard compiler choice for Shader Model 6 rather than a new shader language; much ordinary HLSL source works with either toolchain.

Shader Model 6 is a versioned family (`6.0`, `6.1`, and later), not one indivisible feature set. Targets look like `vs_6_0` and `ps_6_0`. Later versions add capabilities such as wave operations, expanded numeric types, ray-tracing library targets, and mesh/amplification shaders, with the exact features depending on the minor version and GPU/driver support. It uses DXIL and support should be queried from the DirectX 12 device when an application depends on a particular version.

The conventional pairings are FXC plus Shader Model 5.1, producing DXBC, and DXC plus Shader Model 6, producing DXIL. DirectX 12 can consume either for an ordinary pipeline when the required device and system support is present. The `.hlsl` source organization need not change when migrating: this project could keep one `Scene.hlsl` with `VSMain` and `PSMain`, changing only the build compiler, target strings, and generated bytecode. A `.cso` suffix merely means “compiled shader object” and can be used for either kind of compiled blob; it does not itself identify DXBC versus DXIL.

> i'm reading https://en.wikipedia.org/wiki/High-Level_Shader_Language
>
> does the "shader model" version only apply to vertex shaders?

## Assistant

No. A shader model is a family of capabilities and stage-specific compilation profiles spanning the programmable shader stages, not a version only for vertex shaders. The stage prefix and model suffix are combined in each compiler target: `vs_5_1` is the vertex-shader profile for Shader Model 5.1, while `ps_5_1` is the pixel-shader profile for the same model. Geometry, hull, domain, and compute shaders likewise use `gs_5_1`, `hs_5_1`, `ds_5_1`, and `cs_5_1`; Shader Model 6 follows the same idea with targets such as `vs_6_0` and `ps_6_0`, plus newer stage or library profiles in later versions.

The Wikipedia article can create the opposite impression because it contains separate historical “Pixel shader comparison” and “Vertex shader comparison” tables. Early Direct3D hardware exposed substantially different vertex and pixel instruction sets and limits. Microsoft describes “Shader Model” as grouping a set of stage profiles, and from Shader Model 4 onward the stages share a common-shader core while retaining stage-specific functions and restrictions. Thus the model number is shared, but individual features are not necessarily available in every stage.

For this project, both existing targets belong to the same Shader Model 5.1 family: `VSMain` is compiled as `vs_5_1`, and `PSMain` as `ps_5_1`. A move to Shader Model 6 would normally update both to matching profiles such as `vs_6_0` and `ps_6_0`; they remain two separately compiled programs.

Sources consulted: the referenced Wikipedia HLSL article and Microsoft Learn's HLSL programming guide, common-shader core documentation, and Shader Model 6.0 documentation.

## User

> explain the difference between each version of shader model version 6.x

## Assistant

Shader Model 6 revisions are cumulative: each minor version retains earlier capabilities and adds specific features. A higher target does not inherently make an ordinary shader faster or prettier, and some features remain optional hardware capabilities that require their own DirectX feature queries. Applications should normally target the lowest shader model containing the features they use.

- 6.0 established the DXC/DXIL generation, adding wave intrinsics and 64-bit integer arithmetic.
- 6.1 added view instancing through `SV_ViewID` and pixel-shader barycentrics through `SV_Barycentrics`/`GetAttributeAtVertex`.
- 6.2 added real 16-bit scalar types usable in memory and selectable floating-point denormal behavior.
- 6.3 added DirectX Raytracing support plus the `lib_6_3` shader-library and linking model.
- 6.4 added variable-rate-shading semantics, packed low-precision dot-product intrinsics, and raytracing library subobjects.
- 6.5 added mesh and amplification shader profiles, DXR 1.1 inline ray queries, sampler feedback, and additional grouped wave operations.
- 6.6 added direct descriptor-heap indexing, expanded 64-bit and limited floating-point atomics, derivatives outside pixel shaders, `IsHelperLane`, pack/unpack operations, explicit wave-size selection, and ray-payload access qualifiers.
- 6.7 added advanced texture operations such as raw gather, explicit-level comparison sampling, programmable offsets, and writable MSAA textures, plus quad voting and an option to include helper lanes in wave operations.
- 6.8 added work-graph node shaders, comparison sampling with bias or gradients, start-vertex/start-instance system values, and wave-size ranges.
- 6.9 makes native 16-bit operations, wave operations, and 64-bit integer operations mandatory for conforming implementations; it also adds opacity-micromap and shader-execution-reordering support for raytracing, correct 16-bit special-float tests, and vectors of 5 through 1024 elements with corresponding DXIL vector support.

As of 2026-08-30, Shader Model 6.10 exists as a preview. Its preview includes linear-algebra matrix operations, thread-group wave indexing/counting, variable groupshared-memory limits, and additional raytracing intrinsics; it should not yet be treated as the stable compatibility target.

For this project's conventional vertex and pixel shaders, none of the specialized 6.1-and-later features is needed. If migrating to DXC, `vs_6_0` and `ps_6_0` are the broadest Shader Model 6 targets and are sufficient. Raising the target should be driven by a concrete feature requirement.

Sources consulted: Microsoft's DirectXShaderCompiler Shader Model documentation, the published DirectX Shader Model 6.5 through 6.9 specifications, and the DirectX Developer Blog's Shader Model 6.10 preview announcement.

## User

> what are the requirements for each version

## Assistant

Shader Model requirements have four layers: DXC must recognize the target, the DirectX 12 runtime/DXIL validator must accept it, the installed GPU driver must report that shader model through `CheckFeatureSupport(D3D12_FEATURE_SHADER_MODEL)`, and any optional advanced feature used by the shader must pass its separate capability query. There is no reliable fixed list of GPU model names because driver updates can change reported support and many shader-model additions are optional features.

The historical stock-Windows runtime baselines were Windows 10 1703 for SM 6.0, 1709 for 6.1, 1803 for 6.2, 1809 for 6.3, 1903 for 6.4, 2004 for 6.5, and Windows 11 for 6.6. The Agility SDK decouples newer user-mode D3D12 runtimes from OS releases: 6.6 is available through the Agility SDK on supported Windows 10 systems, 6.7 through Agility SDK 1.606.3, 6.8 through 1.613, and retail 6.9 through 1.619 with DXC 1.9.2602.16 or newer. Shader Model 6.10 remains preview-only and currently requires Agility SDK 1.720/1.721 preview, the corresponding preview DXC 1.10, preview-capable drivers, and the preview setup requirements.

For all stable versions, a current stable DXC can compile older targets; an old matching compiler is unnecessary. Runtime code must query the device rather than infer support from the Windows version. SM 6.0 wave and int64 operations have separate support flags; SM 6.1 view instancing and barycentrics have capability checks; SM 6.2 native 16-bit operations require their device flag and `-enable-16bit-types`; SM 6.3 raytracing requires an appropriate DXR tier; SM 6.4 VRS requires a VRS tier; SM 6.5 mesh shaders, sampler feedback, and DXR 1.1 require their corresponding tiers; SM 6.6 advanced atomics require their support flags; SM 6.7 advanced texture operations are optional; SM 6.8 work graphs require a work-graphs tier; and SM 6.9's raytracing features require the relevant DXR support even though native 16-bit, wave, and int64 shader operations become mandatory for a device reporting SM 6.9.

Direct3D feature level and shader model are separate axes. This project creates a DirectX 12 device at feature level 11_0, which does not by itself prevent Shader Model 6; the renderer should add a shader-model query if migrated to DXC. Its simple vertex and pixel shaders need only `vs_6_0` and `ps_6_0`, so the runtime requirement would be a DirectX 12 device whose driver reports at least `D3D_SHADER_MODEL_6_0`; none of the optional wave, raytracing, mesh, VRS, or native-16-bit features is needed.

Sources consulted: Microsoft Learn's `D3D_SHADER_MODEL` and `D3D12_FEATURE_DATA_SHADER_MODEL` documentation, the DirectX 12 release history, the DirectXShaderCompiler documentation, the Agility SDK support and release pages, and Microsoft's Shader Model 6.7, 6.8, 6.9, and 6.10 announcements.

## User

> what hardware is needed for each version of 6.x

## Assistant

There is no authoritative fixed GPU-generation table for base Shader Model 6 targets. The exact hardware requirement for `vs_6_x` or `ps_6_x` is a DirectX 12 adapter whose installed driver reports at least `D3D_SHADER_MODEL_6_x` through `CheckFeatureSupport`. Shader Model is a driver/runtime execution contract rather than a direct silicon-generation label; driver updates and software implementations can change or emulate support. The GPU model name, DirectX feature level, Windows version, and shader-model number cannot substitute for the query.

For ordinary vertex and pixel shaders, the base requirement at each revision is simply driver-reported support for 6.0, 6.1, and so on. The headline features added by a revision frequently require additional hardware capabilities: waves/int64 for 6.0; view instancing/barycentrics for 6.1; native 16-bit operations for 6.2; DXR for 6.3; VRS for 6.4; mesh shaders, sampler feedback, or DXR 1.1 for 6.5; advanced atomics for 6.6; advanced texture operations for 6.7; Work Graphs for 6.8; and relevant DXR capabilities for the raytracing portions of 6.9. A GPU may accept a plain shader targeting a given model without supporting every optional headline feature from that model.

Concrete cross-vendor hardware lists therefore apply to particular features, not to every plain shader target. DirectX 12 Ultimate-class functionality associated with the 6.5 era broadly maps to NVIDIA RTX, AMD RDNA 2/Radeon RX 6000, and Intel Arc-class hardware, but each tier still needs querying. At the retail launch of Work Graphs, Microsoft listed AMD Radeon RX 7000 and NVIDIA RTX 30-series or newer with appropriate drivers. Microsoft's retail SM 6.9 feature table lists NVIDIA RTX hardware, Intel Arc B-series, and AMD RX 9000 for long vectors/16-bit special-float operations; OMM and SER support/performance differ further. Shader Model 6.10 remains preview-only, with feature-by-feature vendor support rather than a general consumer baseline.

For this project's simple shader, `vs_6_0`/`ps_6_0` needs no optional Shader Model 6 features. The broad and correct hardware policy is to attempt a DirectX 12 device and require `HighestShaderModel >= D3D_SHADER_MODEL_6_0`; retain the existing SM 5.1 bytecode as a fallback only if support for older drivers matters. Targeting a higher model without using its features would unnecessarily reject hardware.

Sources consulted: Microsoft Learn's shader-model capability-query documentation, Microsoft's DirectXShaderCompiler/DXIL documentation, the DirectX 12 Ultimate feature-level announcement, Microsoft's Work Graphs hardware list, the retail SM 6.9 hardware-support table, and the SM 6.10 preview hardware table.

## User

> ultimately, what i want to do is reimplement https://github.com/kvu787/ZoomTracks as an engine-less game that only uses this shader: https://github.com/kvu787/SimplePaintShaders, and target sustained fps in the 1,000 to 5,000 fps range. given this, what choices should i make.

## Assistant

For that specific goal, I would build a deliberately tiny native Direct3D 12 program, use the Simple Paint shader as its only material shader, and treat **0.2-1.0 ms CPU/GPU frame time** as the engineering target. I would not define success as 1,000-5,000 visibly displayed frames per second: a 360 Hz monitor can scan out at most 360 complete refreshes per second, and excess `Present` calls may be torn or discarded. The high-rate target is still useful as render-time and simulation-latency headroom.

| Decision | Choice |
|---|---|
| Platform | Win32, C++20, Direct3D 12, DXGI, DirectXMath, GameInput |
| Shader source | One external `shaders/SimplePaint.hlsl` containing `VSMain` and `PSMain` |
| Compilation | Build-time DXC, compiled once as `vs_6_0` and once as `ps_6_0` |
| Packaging | Embed the two resulting DXIL blobs in the executable |
| Rendering | Orthographic, unlit, one PSO, no MSAA/TAA/post-processing/shadows |
| Simulation | Fixed 1,000 Hz, independent of rendering |
| Presentation | Separate low-latency display mode from uncapped benchmark mode |
| Assets | Offline conversion to small custom binary mesh/collision formats |

Use Shader Model 6.0, not the newest Shader Model. The shader does not need ray tracing, mesh shaders, work graphs, advanced atomics, or other later features, and a higher target does not automatically make ordinary shader code faster. DXC is the right modern compiler, but use it during the build rather than at runtime. This keeps the HLSL separate and editable while avoiding compiler work, compiler DLLs, and file-path failures in the released game. The one source file is still compiled twice because it contains two GPU programs: a vertex entry point and a pixel entry point. [DXC's documented role is compiling SM 6 HLSL into DXIL.](https://github.com/microsoft/DirectXShaderCompiler)

Port the current `K12.gdshader` faithfully before optimizing it. It is already unlit and disables shadows, fog, ambient light, and specular work. More importantly, its own comments say that all material-derived values should be computed by the CPU; do that once when a material is loaded or changed, rather than recomputing sine, cosine, and color coefficients per vertex. Because ZoomTracks uses an orthographic camera, the view direction is constant across the image: transform normals into view space in the vertex shader, interpolate them, normalize in the pixel shader, and remove the current per-pixel view normalization and basis construction. Keep 32-bit floats initially; test a Shader Model 6.2/FP16 variant only if profiling identifies the pixel shader as the bottleneck and image comparisons show no visible change. [The shader source and its optimization notes are here.](https://github.com/kvu787/SimplePaintShaders/blob/main/Godot/ShaderTest/Shaders/K12.gdshader)

For the first complete renderer, draw the flattened track geometry and the car with that same shader every frame. Merge static geometry by material and aim for a handful of indexed draws, not a complex general-purpose scene system. Use immutable GPU-local vertex/index buffers, one root signature and PSO, preallocated command allocators, and a persistently mapped upload ring for the camera and car transforms. Create nothing, allocate nothing, compile nothing, and log nothing in the hot loop. Start with the shader's two-sided behavior for visual fidelity; test back-face culling later on closed vehicle meshes. Use a depth buffer for the car's self-occlusion, but disable MSAA, TAA, lighting, shadows, fog, HDR, and post-processing.

The static environment creates a useful second-stage optimization. ZoomTracks explicitly describes the environment as static and flattenable to a 2D image. For the fixed-camera view, render it once with Simple Paint into a GPU texture, copy that image into each back buffer, then draw the moving car; this still requires no second shader. Rebuild the cache when the view or zoom changes. Smooth arbitrary follow-camera motion is different: integer texture copies cannot perform subpixel sampling or scaling. The clean high-performance solution is a tiny texture-blit/composite shader, making Simple Paint the only **material** shader rather than literally the only pixel shader. If the literal one-shader restriction is absolute, redraw the track during smooth follow/zoom. I would implement direct redraw first and relax this restriction only if profiling shows that the 5,000-FPS target requires caching. [ZoomTracks' own description supports this static-world split.](https://github.com/kvu787/ZoomTracks/blob/main/README.md)

Keep the game loop single-threaded initially: nonblocking Win32 message pump, read the newest GameInput sample, advance fixed-step 2D simulation/collision, record the tiny command list, submit, and present. A fixed 1,000 Hz simulation gives deterministic behavior and at most roughly 1 ms of simulation sampling delay without pointlessly tying physics to a potentially 5,000 Hz render loop. GameInput is preferable to XInput for this project because it exposes timestamped readings and is Microsoft's recommended new-code input API; use timestamps and sequence numbers to measure the Razer controller's actual reports rather than assuming every poll is new. [GameInput readings are timestamped in microseconds.](https://learn.microsoft.com/en-us/gaming/gdk/docs/reference/input/gameinput/interfaces/igameinputreading/igameinputreading)

Provide two runtime modes because throughput and display latency require opposing queue policies:

- **Play mode:** borderless flip-discard swap chain, two buffers, tearing support, `Present(0, DXGI_PRESENT_ALLOW_TEARING)`, frame-latency waitable object, and maximum frame latency 1. This prioritizes a fresh frame and prevents the CPU from building a latency-producing queue. Microsoft recommends flip model, and tearing is the DXGI mechanism required for VRR. [Flip-model guidance](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model), [VRR/tearing requirements](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/variable-refresh-rate-displays).
- **Benchmark mode:** render offscreen or run with a small ring of in-flight command allocators without waiting on display cadence. Measure CPU production, GPU execution, and presentation separately. Do not call an offscreen 5,000-FPS result “display FPS.”

At 2560x1440, one full-screen pass at 1,000 FPS represents about 3.69 billion pixel invocations per second; at 5,000 FPS it is 18.43 billion. The paint shader contains square roots, divisions, and normalization, so 5,000 FPS at native resolution is a measurement question even on the RTX 5090 laptop, not something the API or Shader Model can guarantee. Also test after the laptop reaches thermal steady state.

Instrument from the beginning. Use `QueryPerformanceCounter` for CPU sections, Direct3D 12 timestamp queries for GPU sections, PresentMon for the presentation path, and PIX to identify the limiting pass. Microsoft specifically recommends PIX and documents D3D12 timestamp calibration/querying for accurate GPU timing. Report frame-time percentiles and worst stalls after warm-up, not just average FPS. [Direct3D 12 timing guidance](https://learn.microsoft.com/en-us/windows/win32/direct3d12/timing).

The implementation order I would use is:

1. Port K12 to `SimplePaint.hlsl` and validate screenshots against Godot.
2. Add build-time DXC `vs_6_0`/`ps_6_0` compilation and embedded bytecode.
3. Port the car simulation and static collision index with a fixed 1,000 Hz step.
4. Convert one track and car offline; render them directly with a minimal number of draws.
5. Add CPU, GPU, and presentation measurements and establish 1,000-FPS frame-time consistency.
6. Only then optimize toward 5,000 FPS: orthographic shader specialization, draw/material consolidation, and—if necessary—the static-background cache.

The important non-choices are just as concrete: no runtime shader compiler, no Shader Model above 6.0 without a measured reason, no engine-like renderer abstraction, no job system, no per-frame asset work, and no claim that uncapped `Present` throughput equals visible or low-latency FPS.

## User

> as part of this reimplementation, ZoomTracks will only render the vehicle as a 3d thing. everything else will be a 2d image.

## Assistant

That simplifies the design and changes one important recommendation: do not load or render track geometry at runtime. Each frame should consist of a background image operation, one indexed draw of the 3D vehicle using Simple Paint, and presentation.

The best exact design depends on the camera:

- With a completely fixed camera and an image already at the output resolution, upload the opaque image once and use `CopyTextureRegion` to copy it to the back buffer each frame. Then clear only the depth buffer and draw the vehicle. This needs no background shader at all.
- If the camera follows the car, moves by subpixels, or zooms, render a full-screen triangle that samples a world/track image with a tiny texture shader. Use offline-generated mipmaps and bilinear or trilinear sampling. Store the world-to-image transform with the track so the background and the vehicle's orthographic view remain aligned.

I would keep camera yaw fixed. Pan/follow and zoom work naturally with a 2D background, but changing the viewing direction cannot reveal correct new views of an already flattened image. This matches the current ZoomTracks implementation, in which camera rotation control is disabled.

There is a semantic distinction in “only uses this shader.” Simple Paint can cleanly be the game's only **3D/material shader**, but its current pixel shader does not sample textures. Smoothly moving or scaling a 2D image therefore requires either a tiny background texture shader or a modified combined shader with a background mode. The clean choice is a separate background entry-point pair; contorting the paint pixel shader with a uniform branch adds complexity without avoiding the fact that two different rendering operations exist.

If one HLSL source file is still desired, `shaders/Scene.hlsl` can contain four entry points:

- `BackgroundVS` and `BackgroundPS`
- `VehicleVS` and `VehiclePS`

DXC would compile that file four times, once for each entry point. Both pairs can target Shader Model 6.0. Use two PSOs: an opaque background PSO with depth disabled, and a vehicle PSO with depth testing/writes enabled. If the fixed-camera copy path is sufficient, omit the background entry points and retain only the two vehicle compilations.

For sampled backgrounds, use an offline-generated DDS texture with mipmaps. BC7 sRGB is a good starting format for a large world image; use an uncompressed RGBA8 image for the fixed-resolution copy path. If the desired world image exceeds the GPU's texture-size limit, split it into fixed-size tiles and render only visible tiles rather than adding a general-purpose asset/scene system.

The steady-state render workload should therefore be only:

1. Copy the fixed background, or draw one full-screen sampled triangle.
2. Clear depth.
3. Bind the vehicle PSO and draw one indexed vehicle mesh.
4. Present.

No color clear is needed because the opaque background covers every pixel. The car shader's square roots and divisions now affect only the small screen area covered by the vehicle, so optimizing it to FP16 or a later Shader Model is unlikely to matter. CPU-precompute its material coefficients and specialize its view math for the fixed orthographic direction, but focus measurement on the full-screen background operation and `Present`.

At 2560x1440 and 5,000 FPS, a full-screen background operation still touches about 18.43 billion pixels per second. An uncompressed texture read plus a 4-byte render-target write represents roughly 147 GB/s of theoretical traffic before caching or compression, so the background is not free even though it is 2D. The 3D car will be comparatively negligible.

All other earlier choices remain: native Win32/C++20/D3D12, build-time DXC with embedded DXIL, fixed 1,000 Hz simulation, GameInput, no MSAA/TAA/post-processing, and separate low-latency play and offscreen-throughput benchmark modes. First validate 1,000 FPS at native resolution with stable frame-time percentiles; treat 5,000 FPS as an offscreen/render-throughput target unless presentation measurements prove otherwise.
